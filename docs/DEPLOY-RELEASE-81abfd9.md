Release commit: **`81abfd9127ea5376a6f56ffb4e98715823b1184b`** (`81abfd9`, `main`, pushed).

**Every block is labelled with the user it runs as.** The sheet moves between `root` and `siws` several times; running a block as the wrong user is the most common way this goes wrong. Never paste `su - siws && cd ~/app` as one line — `su` consumes the rest of the paste as its stdin and the `cd` runs later, in root's shell, in a directory that does not exist.

## A1. Server user and packages — **as `root`**

Ubuntu 24.04 ships `needrestart` in interactive mode; without these two lines `apt upgrade` opens a whiptail dialog that swallows the rest of your paste and leaves the box with no Node.

```bash
export DEBIAN_FRONTEND=noninteractive
sed -i "s/^#\$nrconf{restart} = 'i';/\$nrconf{restart} = 'a';/" /etc/needrestart/needrestart.conf 2>/dev/null || true

adduser --disabled-password --gecos "" siws

# siws is created with no password, so group membership alone gives it no sudo.
# Give it working, non-interactive sudo before anything needs it.
printf 'siws ALL=(ALL) NOPASSWD:ALL\n' > /etc/sudoers.d/90-siws
chmod 440 /etc/sudoers.d/90-siws
visudo -c

apt update
apt-get -y -o Dpkg::Options::=--force-confold -o Dpkg::Options::=--force-confdef upgrade
apt install -y curl git nginx ufw ca-certificates rsync bind9-dnsutils
curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
apt install -y nodejs
node -v | grep -q '^v22\.' && echo "node OK" || echo "STOP: NODE MISSING"
npm install -g pm2
```

SSH access for `siws` — this must come **after** the apt install, and it must not assume `/root/.ssh` exists (on a Hostinger VPS you usually log in as root with a password, so it does not):

```bash
install -d -m 700 -o siws -g siws /home/siws/.ssh
if [ -f /root/.ssh/authorized_keys ]; then
  install -m 600 -o siws -g siws /root/.ssh/authorized_keys /home/siws/.ssh/authorized_keys
  echo "key copied"
else
  echo "NOTE: root has no authorized_keys. Either paste your public key into"
  echo "/home/siws/.ssh/authorized_keys now, or ship the dump to root in A6."
fi
```

Firewall — SSH and web only; Postgres is never exposed:

```bash
ufw allow OpenSSH
ufw allow 'Nginx Full'
ufw --force enable
ufw status
```

Swap, only if the box has under 4 GB RAM (`next build` peaks around 1.2 GB). Guarded, so re-running it on an existing server does not append a duplicate `/swapfile` line to `/etc/fstab` or fail halfway on an active swapfile:

```bash
if ! swapon --show | grep -q '/swapfile' && [ "$(free -m | awk '/^Mem:/{print $2}')" -lt 4000 ]; then
  fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
  grep -q '^/swapfile ' /etc/fstab || echo '/swapfile none swap sw 0 0' >> /etc/fstab
fi
swapon --show
free -h
```

## A2. PostgreSQL 18 — NOT the distro package — **as `root`**

The development database is **PostgreSQL 18.6**. Ubuntu 24.04's `postgresql` metapackage is **16**, and the dump contains `SET transaction_timeout` (PG17+) and `\restrict` (PG18) — a restore into 16 aborts. Install from PGDG:

```bash
apt install -y postgresql-common
/usr/share/postgresql-common/pgdg/apt.postgresql.org.sh -y
```

**If the box already has a PG16 cluster on 5432, drop it first** — a cluster's port is fixed when the cluster is created, so if 16 still owns 5432 at install time, 18 is created on 5433 and *stays there*. Dropping 16 afterwards does not renumber anything.

```bash
pg_lsclusters
# ⚠ destroys any PG16 data on this box — check the diagnostic's row counts first
pg_dropcluster --stop 16 main
apt purge -y postgresql-16
```

Then install 18:

```bash
apt install -y postgresql-18
pg_lsclusters
psql --version         # expect psql (PostgreSQL) 18.x
```

If `pg_lsclusters` shows `18 main` on **5433** (because 16 was still present when 18 was installed), move it — the whole rest of the sheet connects to 5432:

```bash
sed -i 's/^port = 5433/port = 5432/' /etc/postgresql/18/main/postgresql.conf
pg_ctlcluster 18 main restart
pg_lsclusters          # DO NOT CONTINUE until this prints: 18 main 5432 online
```

## A3. Database and role — **as `root`**

Generate a **URL-safe** password. `openssl rand -base64` produces `+ / =`, and a `/`, `@` or `:` inside a `postgres://user:pass@host/db` URI silently reparses the host and database — it fails identically in `.env`, in every `psql` line and in cron.

```bash
openssl rand -hex 32          # -> use as <DB_PASSWORD>
sudo -u postgres psql
```

At the `postgres=#` prompt:

```sql
CREATE ROLE siws WITH LOGIN PASSWORD '<DB_PASSWORD>';
CREATE DATABASE siws OWNER siws;
\q
```

Prove the login works before going further — the output must name database `siws` on port `5432`:

```bash
psql "postgres://siws:<DB_PASSWORD>@localhost:5432/siws" -c '\conninfo'
```

## A7. Restore on the server — **as `siws`**

The dump carries the **schema as well as the content** — there is no `src/migrations/` and production does not create tables. Nothing works without this step.

`gunzip -k` keeps the archive, and `--single-transaction` means a failure rolls back cleanly instead of leaving you with a half-populated database and no dump left on the box.

```bash
cd ~/app || exit 1
[ -f .env ] || { echo "WRONG DIRECTORY"; exit 1; }
set -a; . ./.env; set +a
: "${DATABASE_URI:?DATABASE_URI not set}"

gunzip -k -f ~/siws.sql.gz
psql -v ON_ERROR_STOP=1 --single-transaction "$DATABASE_URI" -f ~/siws.sql
```

Do not run certbot until both print `OK`. Failed HTTP-01 validations burn Let's Encrypt's five-per-hour limit and lock you out for an hour on go-live night.

The `Connection` header must be `upgrade` only for real WebSocket upgrades — hard-coding it disables keepalive to the Next server on every ordinary request:

```bash
tee /etc/nginx/conf.d/upgrade-map.conf > /dev/null <<'NGINX'
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
NGINX

tee /etc/nginx/sites-available/siws > /dev/null <<'NGINX'
server {
    listen 80;
    server_name siwsschool.edu.in www.siwsschool.edu.in;

    # src/collections/Media.ts: MAX_IMAGE_BYTES = 12 MB, MAX_PDF_BYTES = 25 MB.
    # 26M covers the PDF ceiling plus multipart boundary/header overhead, so the
    # app issues its own readable rejection instead of nginx returning a bare 413.
    client_max_body_size 26M;

    location /_next/static/ {
        proxy_pass http://127.0.0.1:3001;
        add_header Cache-Control 'public, max-age=31536000, immutable';
    }

    location / {
        proxy_pass         http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection $connection_upgrade;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
        proxy_read_timeout 120s;
    }
}
NGINX

ln -sf /etc/nginx/sites-available/siws /etc/nginx/sites-enabled/siws
rm -f /etc/nginx/sites-enabled/default
nginx -t && systemctl reload nginx
```
